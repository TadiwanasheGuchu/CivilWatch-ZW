# 03 — Database Design

PostgreSQL 16 with PostGIS 3. Migrations are managed by Alembic (`backend/alembic/`).

## Conventions

- UUID primary keys (`UUIDPrimaryKeyMixin`), generated by the application.
- `created_at` / `updated_at` as `timestamptz`, stored in UTC (sessions run with `timezone=UTC`).
- Deterministic constraint names via the naming convention in `app/models/base.py`.
- Every council-owned table carries a non-null `council_id` foreign key.
- Geometry uses SRID 4326; points as `geography(Point, 4326)` for distance queries, council boundaries as `geometry(MultiPolygon, 4326)`; GiST indexes on every spatial column.
- Migrations are additive; destructive changes need a documented data-migration plan.

### `issue_status_history`

Append-only: one row per status change. Columns: `id`, `issue_id` (FK, restrict), `from_status` (null for submission), `to_status`, `changed_by_user_id` (FK, set null), `created_at` (set by the application so inserts need no `RETURNING`). Index `(issue_id, created_at)`.

### `issue_media`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | Also part of the object keys |
| `issue_id` | uuid FK → issues (restrict) | |
| `uploaded_by_user_id` | uuid FK → users (set null), null | |
| `display_key`, `thumbnail_key` | varchar(255), unique | Object keys `issues/{issue_id}/{media_id}/display.jpg` and `…/thumbnail.jpg`; never URLs |
| `content_type` | varchar(32) | Check: `image/jpeg` (every upload is re-encoded) |
| `kind` | varchar(16), default `report` | Check: `report` (from the reporter) or `repair` (evidence from staff doing the work) |

| `created_at` | timestamptz | Set by the application |

Index `(issue_id, created_at)`. Reports load their photos with one extra query per page (`selectin`), never one per report.

### `departments`

`id`, `council_id` (FK), `name` (citext; unique per council; 2–80 characters), `description`, `is_active`, timestamps. A unique `(id, council_id)` lets other tables require that a department belongs to the same council.

`council_memberships.department_id` (nullable) references `departments(id, council_id)` together with the membership's `council_id`, so a membership can never point at another council's department.

### `issue_assignments`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `issue_id`, `council_id` | uuid | Composite FK → `issues(id, council_id)` |
| `department_id` | uuid | Composite FK with `council_id` → `departments(id, council_id)` |
| `assignee_user_id` | uuid FK → users, null | Optional officer |
| `assigned_by_user_id` | uuid FK → users (set null) | |
| `created_at`, `ended_at` | timestamptz | Reassignment ends the current row and adds a new one |

Partial unique index `uq_issue_assignments_current` on `issue_id WHERE ended_at IS NULL`: at most one current assignment per report. Indexes on assignee and department.

### `issue_updates`

Staff-only working notes: `id`, `issue_id` + `council_id` (composite FK), `author_user_id`, `body` (1–2000), `created_at`. Append-only.

### Other changes in 0007

`issues.duplicate_of_issue_id` (FK → issues) and a unique `(id, council_id)`; `issue_status_history.note` (≤1000 characters), the message to the reporter.

### `notifications`

`id`, `user_id` (FK, cascade), `issue_id` (FK, cascade), `kind` (`status_changed`, `information_requested`, `information_provided`, `work_assigned`, `feedback_not_fixed`), `title` (≤160), `body`, `link` (check: a relative in-app path), `created_at` (set by the application), `read_at`, `email_sent_at`, `email_attempts` (default 0), `email_last_error` (≤300). Indexes: `(user_id, created_at)`, a partial index on unread rows per user, and a partial index on `created_at` for rows not yet emailed.

`users.email_notifications` (boolean, default true) is the person's email preference.

### `resolution_feedback`

`id`, `issue_id` (FK, unique — one answer per report), `council_id`, `reporter_id`, `fixed` (boolean), `comment` (≤1000), `created_at`. Index on `council_id` for analytics.

## Database roles and Row-Level Security

| Role | Used by | Privileges |
|---|---|---|
| Schema owner (`POSTGRES_USER`) | Alembic only | Owns all tables and the RLS helper functions |
| `civicwatch_worker` | Email delivery task | `users`: SELECT of `id`, `email`, `full_name`, `is_active`, `email_notifications` only (never password hashes) · `notifications`: SELECT of the columns an email needs, UPDATE of `email_sent_at`, `email_attempts`, `email_last_error` only. RLS policies for this role allow all notification rows. No access to reports, photos or anything else |
| `civicwatch_app` | API and the session-purge task | `users`, `user_sessions`: SELECT/INSERT/UPDATE/DELETE · `councils`, `council_memberships`: SELECT/INSERT/UPDATE · `audit_logs`, `issue_status_history`: SELECT/INSERT only (append-only) · `issues`: SELECT/INSERT, UPDATE of `status`, `duplicate_of_issue_id`, `updated_at` only · `issue_media`: SELECT/INSERT/DELETE · `departments`: SELECT/INSERT, UPDATE of name/description/is_active · `issue_assignments`: SELECT/INSERT, UPDATE of `ended_at` · `issue_updates`: SELECT/INSERT · `notifications`: SELECT/INSERT, UPDATE of `read_at` · `resolution_feedback`: SELECT/INSERT · `issue_categories`: SELECT |

The API sets the transaction-local setting `app.user_id` for every transaction of an authenticated request (`app/core/database.py`). Policies:

- `council_memberships` — read: own rows, rows of councils where the user is an active member, or platform admin. Insert/update: councils where the user is an active `council_admin`, or platform admin. No delete.
- `audit_logs` — read: platform admin, or `council_admin` of the entry's council. Insert: only as yourself (`actor_user_id` is null or the current user).
- `issues` — read: the reporter, active staff of the report's council, or anyone (including anonymous requests) when the report is `PUBLIC` and published (`VERIFIED`, `ASSIGNED`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`). Insert: only as yourself and only with status `SUBMITTED`. Platform admins get no special access.
- `issue_media` — read: exactly when the report is readable. Reporters insert and delete only `report` photos of their own report while it is `SUBMITTED` or `NEEDS_INFORMATION`. Council staff insert `repair` photos for their council's reports while `IN_PROGRESS` or `RESOLVED` (which staff exactly is decided by the workflow rules). Nobody else may insert, and repair photos cannot be deleted through the API.
- `issues` (update) — staff of the report's council; or the reporter, only from `NEEDS_INFORMATION` and only to `UNDER_REVIEW`. Which staff may make which change is decided by the workflow rules in the API.
- `departments` — read: council staff. Insert/update: the council's administrators.
- `notifications` — read and mark read (`read_at` only; the API role cannot touch the email columns): the recipient. Insert: any signed-in person, but only about a report they can themselves read.
- `resolution_feedback` — read: the reporter and the council's staff. Insert: the reporter, for their own report, once it is `RESOLVED` or `CLOSED`.
- `issue_assignments`, `issue_updates` — read: council staff only (never residents or the public). Insert: council staff, as themselves.
- `issue_status_history` — read: exactly when the report is readable (the policy's subquery runs under the `issues` policies). Insert: only as yourself, for a report you can read.

Helper functions `app_current_user_id()`, `app_is_platform_admin()`, `app_member_council_ids()` and `app_admin_council_ids()` are `SECURITY DEFINER` (owner) so policies on `council_memberships` do not recurse into themselves.

Because PostgreSQL applies *read* policies to `INSERT … RETURNING`, rows that an actor may write but not read (audit entries) must not need `RETURNING`: `audit_logs.occurred_at` is therefore set by the application, not by a server default.

`users`, `user_sessions` and `councils` have no RLS: sign-in must look up users before an identity exists, and the council directory is public. Access to them is controlled in the service layer.

Stale sessions (expired, revoked or idle for more than a day past the limit) are deleted hourly by the `identity.purge_stale_sessions` Celery task.
