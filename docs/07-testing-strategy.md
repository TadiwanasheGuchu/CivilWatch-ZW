# 07 — Testing Strategy

## Layers

| Layer | Tool | Location | Runs against |
|---|---|---|---|
| Backend unit/API | Pytest + HTTPX (`TestClient`) | `backend/tests/` | Real PostgreSQL + PostGIS and Redis — no database mocks |
| Frontend unit/component | Vitest + Testing Library | `frontend/**/*.test.ts(x)` | jsdom; `fetch` stubbed per test |
| End-to-end | Playwright | `frontend/tests/e2e/` | Running Next.js + real API |

Backend tests apply all Alembic migrations once per session, so every run also proves the migrations work. After each test the application tables are truncated and the Redis database flushed; the suite refuses to run unless `CIVICWATCH_ENVIRONMENT=test`. The test client uses an `https://` base URL so `Secure` cookies behave as in production. CI additionally runs `alembic check` to catch models without a migration.

Playwright runs every spec at 320, 375, 390, 768, 1024 and 1440 px widths and asserts no horizontal scrolling and ≥44px touch targets.

## Current coverage

- API conventions: error envelope (404/405), request-ID generation, propagation and sanitisation, security headers, CORS allow/deny, OpenAPI path, docs disabled in production.
- Health: liveness, readiness OK, readiness degraded (503) when Redis is down.
- Authentication: registration (normalisation, Argon2id storage, hashed session tokens, hardened cookie attributes, duplicate emails, validation incl. privilege-field injection), sign-in (identical failures for wrong password/unknown email, inactive users, account lockout and reset, per-IP registration limit), sessions (absolute and idle expiry, activity extension, forged cookies, server-side revocation on logout and re-login, replay of a revoked cookie), CSRF (missing token, token from another session), cross-origin login rejected, credentials absent from logs.
- Account: own profile only, CSRF on updates, no privilege escalation, password change signs out other sessions, wrong current password and its rate limit, stale-session purge.
- Settings: production refuses insecure cookies; `__Host-` cookies require `Secure`.
- Councils: public directory and pagination, creation limited to platform admins (with CSRF and slug rules), workspace permissions per role, residents and unknown councils refused, platform admin without operational access.
- Staff management: add/change/remove with immediate loss of access, re-appointment keeps history, unknown email/duplicate/invalid role, officers cannot add staff or promote themselves, last administrator protected, every change audited with actor and request ID.
- **Tenant isolation (mandatory)**: council A's administrator cannot read B's workspace, staff or audit log, cannot add, change or remove B's staff, cannot reach B's membership through A's URL, sees only A's rows in lists; council IDs in bodies are rejected; a person in two councils has the right role in each.
- **Row-Level Security at the database**, as the API's role: the role cannot bypass RLS; unfiltered queries return only the user's councils; no identity → no rows; residents see nothing; cross-council inserts are refused and updates affect no rows; the audit log cannot be updated or deleted; audit entries cannot impersonate another actor; the identity does not leak between transactions on pooled connections.
- Operator CLI: granting and revoking platform admin, audited.
- Staff sessions: idle and lifetime limits end staff and platform-admin sessions (and revoke them), residents keep longer sessions, former staff return to resident limits; settings reject staff limits longer than resident limits.
- Reports: public categories; submission needs sign-in and CSRF; a full submission (reference, status, coordinates, history); sequential references; invalid title/description/control characters/coordinates/visibility; injected `status` and `reporter_id` rejected; unknown or inactive council and unknown category as field errors; location outside the service area; council boundary enforced when known; per-user rate limit; "my reports" shows only your own (including private) with pagination.
- **Report visibility (mandatory)**: only verified PUBLIC reports are listed or readable publicly (unverified, private, rejected and duplicate are `404`), the reporter still sees all of theirs, public responses never identify the reporter, another resident's private report is `404`, and nobody — owner or not — can modify a report through the API. Public filters by council, category and status, with invalid filters rejected.
- **Report RLS at the database**, as the API's role: anonymous connections see only published public reports; residents see their own plus published; council staff see their own council's reports only; history follows report visibility; no filing in someone else's name; no creating pre-verified reports; no updates or deletes of reports or history.
- Photos: GPS and camera metadata removed from stored photos and thumbnails; camera rotation applied; large photos resized; PNG (with transparency), greyscale PNG and WebP converted to JPEG; HTML, PDF, empty, GIF, BMP and truncated files refused; script appended to a JPEG not stored; decompression bomb refused; oversized upload refused (413); sign-in and CSRF required; only the reporter may upload; 5-photo limit; no photos once the council has started; storage outage gives 503 with nothing recorded; reporter gets short-lived signed URLs; photos of private or unpublished reports reach no one else (no signed URLs anywhere in their responses); published public photos are visible to everyone; no unsigned or long-lived URL is ever returned; RLS blocks media rows for someone else's report. Readiness reports storage and degrades when it is down.
- **Storage enforcement (CI only)**: against real MinIO, an unsigned or tampered URL returns 403 and a signed URL stops working after it expires. These two tests are skipped when the local `moto` emulator is used, because moto does not validate signatures.
- Photo removal: the reporter can remove a photo before review (objects deleted too); CSRF, other users, unknown photos and reviewed reports are refused; RLS blocks deletes by others and after review.
- **Council workflow** (stage 3.1): the full lifecycle with each role doing its part, and the reporter seeing the council's messages; each role is offered exactly the transitions it may make.
  - **Invalid transitions are rejected (mandatory)**: every skip from `SUBMITTED`, terminal statuses, unknown statuses, missing required notes. Two simultaneous changes cannot both succeed (threaded test).
  - **Unauthorised staff cannot assign (mandatory)**: verification and maintenance officers are refused; managers cannot assign to, or take reports from, another department; assignees must belong to the chosen department; unverified reports and inactive departments cannot be assigned; reassignment keeps status and history.
  - Work scope: only the assignee or their department's manager can start or resolve work; officers cannot close; reopening needs a reason. Duplicates need an original in the same council.
  - Information requests: the reporter sees the question, can add photos, answers once (a second answer is `409`), and nobody else can answer.
  - Queue, summary and search (references, literal `%` and `_`), staff see the reporter's name but never their email, residents and platform admins are refused, another council's staff can neither see nor change the reports, staff-only notes never reach residents or the public, the public timeline shows no messages, departments and staff departments follow the rules, and RLS enforces the same limits directly in the database.
- Repair photos (stage 3.2): only the assignee, their manager or an administrator, only while in progress or just resolved; their own limit; sanitised; shown to the reporter but never removable by them; private reports' repair photos stay private; RLS refuses repair photos from reporters and outsiders.
- Maps and places (stage 4.1): boundaries set by platform admins only, from a Polygon, MultiPolygon, Feature or FeatureCollection; invalid shapes, swapped coordinates, places outside Zimbabwe, wrong geometry types and malformed GeoJSON are explained; overlaps reported; boundaries cleared; public boundary list (sample flag, MultiPolygon, inactive councils hidden, cache header); locate (smallest area first, empty outside, invalid coordinates); the sample loader (creates councils, labels samples, never overwrites official boundaries) and reports outside a sample boundary refused; public clusters contain only published public reports at every zoom, with filters and bbox/zoom validation; staff clusters include private reports of their own council only; nearby search sorted by real distance, radius limited, never leaking unpublished reports; staff nearby finds same-council duplicates only. Map and locate queries are checked to use the GiST indexes.
- Map helpers (unit): boundary bounding boxes across MultiPolygons, distance wording.
- Notifications and feedback (stage 5.1): the reporter is told about each change with the council's message; information requests and answers reach the right people (never the actor themselves); officers are told about work assigned to them, not about assigning themselves; other staff hear nothing about private reports; unread counts, marking one or all read, and nobody reading or marking someone else's notifications; sign-in and CSRF required. Feedback only after resolution and only once, by the reporter only; "not fixed" alerts the resolving officer and reopens nothing; feedback never appears publicly; RLS refuses spoofed notifications and early feedback.
- Frontend unit/component: API mutation helper (CSRF header, credentials, 204), server field-error mapping, user-facing error messages (rate limits, network, 5xx), `?next=` redirect safety, form schemas, `Field` accessibility wiring, sign-in form (validation, safe redirect, API errors, lockout message, password toggle), staff row (confirmation before removal, explicit role save, API refusal shown), audit action descriptions, session cache cleared when the user changes.
- Email delivery (stage 5.2, against a local `aiosmtpd` server): a notification is emailed once, with an absolute link and opt-out instructions; turning emails off stops them but keeps in-app notifications; profile updates need something to change; failures are retried until the limit and each notification is tried at most once per run; notifications older than 48 hours and deactivated accounts are skipped; without SMTP settings the task does nothing; the worker role cannot read reports or password hashes or change notification text, and the API role cannot mark emails sent.
- Analytics and exports (stage 5.3): performance figures (counts, medians on backdated reports, categories, feedback share), department workload and oldest job, the period limit and an invalid period, an empty council, refusal for residents, signed-out visitors, platform administrators and another council's staff, and no counting of another council's reports. Public statistics with only private and unverified reports are all zero; with verified public reports the counts, the median from verification to fix and the council filter are right, and no titles, coordinates or reporter details appear. Exports: columns, order, current department, no reporter email, formula escaping, audit row with the count, permission per role, council and period scoping, bad ranges.
- Hardening (stage 6.1): oversized JSON and oversized chunked bodies without `Content-Length` are refused with `413`, photo uploads keep their larger limit; HSTS only when deployed; each expensive public endpoint and the export are rate-limited; deployed settings are refused with plain HTTP, missing storage credentials, no separate migration URL, email without the worker role, or SMTP without TLS. CORS origins are read from plain comma-separated or JSON values; hosted `postgres://` URLs get the psycopg driver. The demo seeder can use a shared password from `DEMO_ACCOUNT_PASSWORD` (never printed, never given to the platform administrator) and does nothing when already seeded. The demo seeder (stage 6.3) needs `--confirm`, labels every report and account, reaches each intended status through the real workflow, produces history and notifications, keeps public figures to verified public reports, and refuses to run twice.
- E2E (all six widths, real API): register → account → sign out → sign in; protected page → sign in → back; field validation and duplicate email; wrong password; name update and password change (other session signed out); turning notification emails off and on, kept after a reload; council administrator adds, re-roles and removes staff, is stopped from demoting the last administrator, and sees each change in the audit log; read-only staff view; resident refused a council workspace; switching between two councils. Reporting: a full report with a photo and GPS location, then the report page and My reports; per-step validation; a draft surviving a reload and a sign-in; offline (send disabled, then sent when back online); a failed photo upload retried without creating a second report; signing out deleting an unsent draft. Council operations: a report goes from the overview tile through review and verification (verification officer), assignment (department manager), My work, start, repair photo and resolution (maintenance officer), and the reporter sees the message and the repair photo; the council asks for information and the reporter answers in the app; a required message is enforced and staff notes never reach the reporter; staff with nothing to do are told so and residents cannot open council pages; administrators add and deactivate departments and change a staff member's department. Maps: the Explore map shows a council's verified report as a marker, the preview links to it, the heatmap replaces markers, and "near me" lists it with its distance; the report form chooses the sample Harare council from the pin, says it is a sample boundary, and lists a similar verified report nearby; staff see their council's private reports clustered on the queue map and a nearby report under "Possible duplicates nearby"; platform admins upload a boundary (swapped coordinates explained), see it saved, and remove it; council administrators do not see the Boundary tab. Map tests place their reports at their own random spots so results from earlier runs cannot crowd them out. Notifications: the bell counts unread updates, the list shows the council's question, opening one goes to the report and marks it read, "mark all as read" clears the count; an officer opens new work from a notification, the reporter answers "not fixed" with a comment, and the officer is notified and sees it on the review page. Performance and progress: an administrator sees the council's figures and department, changes the period and downloads a CSV containing both reports but no reporter name or email; a verification officer sees figures without the export; the public progress page, reached from the home page, counts the council's fixed public report but not its private one. Security headers: pages send the CSP and HSTS, and the Explore page with its map runs without any CSP violation. Browsing: Explore shows only verified public reports and never the reporter's name; another resident's private report is "not found"; navigation reaches every resident page (bottom bar on phones, header on wider screens).
- Report submission logic (unit): the report is created once; already-uploaded photos are skipped on retry; a failed create leaves the draft untouched.
- Frontend: API error mapping; status panel OK, degraded and unreachable states.
- E2E: home page layout at six widths; live status from the real API; touch target size.

## Mandatory security tests (added with the features they protect)

Cross-council private-report access · residents modifying others' reports · unauthorised assignment · public access to private media · private data in public analytics · invalid status transitions.

## Running locally

E2E tests need the API (as `civicwatch_app`, with `CIVICWATCH_SESSION_COOKIE_NAME=cw_session`, `CIVICWATCH_SESSION_COOKIE_SECURE=false` for plain-HTTP localhost, and raised `CIVICWATCH_REGISTRATIONS_PER_IP` / `CIVICWATCH_LOGIN_ATTEMPTS_PER_IP` / `CIVICWATCH_PUBLIC_READS_PER_IP`) and a production build of the frontend. They appoint platform admins through the operator CLI, using `E2E_BACKEND_PYTHON` (default `backend/.venv/bin/python`) with the same database environment variables. Test accounts use unique `@example.com` addresses, so runs do not collide.

```bash
cd backend && pytest
```

```bash
cd frontend && npm test && npm run test:e2e
```

Photo tests start a local `moto` S3 server automatically. To use real storage instead, set `CIVICWATCH_TEST_EXTERNAL_STORAGE=1` with the `CIVICWATCH_STORAGE_*` variables, and `CIVICWATCH_TEST_STORAGE_ENFORCES_AUTH=1` to run the enforcement tests.

Backend tests need a disposable database (e.g. `civicwatch_test`) with the `civicwatch_app` login role, and Redis:

- `CIVICWATCH_DATABASE_URL` — as `civicwatch_app` (so RLS is exercised exactly as in production);
- `CIVICWATCH_MIGRATION_DATABASE_URL` — as the schema owner (migrations and per-test cleanup);
- `CIVICWATCH_REDIS_URL`.
